# Задание 10. Миграция на Cassandra

Проблема: в "чёрную пятницу" при 50 000 rps добавление
новых шардов в MongoDB запускало полное перераспределение данных между узлами,
и latency проседала в самый пик.


## 10.1. Какие данные переносить в Cassandra

### Переносим: orders

История заказов — самый большой и самый быстрорастущий объём. Заказы
пишутся один раз и больше не меняются, кроме статуса. На мой взгляд — это идеальный
профиль для Cassandra

### Переносим: carts

Корзины создаются и умирают постоянно, чистятся по TTL. Нагрузка на запись огромная, требования к консистентности не высокие — если корзина гостя на секунду разъедется между репликами, ничего
страшного не произойдёт

### Переносим: пользовательские сессии

Короткоживущие, пишутся на каждый запрос, читаются по ключу

### НЕ переносим: остатки товаров

Списание остатка — операция "прочитать и уменьшить" и она требует гарантии, что никто не уменьшил параллельно.

В Cassandra таких гарантий нет: запись разрешает конфликты по принципу побеждает та, у которой больше метка времени. Два одновременных списания одного товара просто затрут друг друга, и магазин
продаст больше, чем есть на складе


## 10.2. Концептуальная модель

### Таблица 1: заказы пользователя

```cql
CREATE TABLE orders_by_user (
    user_id     uuid,
    created_at  timestamp,
    order_id    uuid,
    status      text,
    total_price decimal,
    items       list<frozen<order_item>>,
    geo_zone    text,
    PRIMARY KEY ((user_id), created_at, order_id)
) WITH CLUSTERING ORDER BY (created_at DESC);
```

`user_id` как partition key: все заказы одного пользователя лежат на одном узле и читаются одним запросом без обхода кластера

`created_at DESC` как clustering key: история сразу отсортирована от новых к старым, сортировать при чтении не нужно


### Таблица 3: корзины

```cql
CREATE TABLE carts_by_owner (
    owner_id   text,
    product_id uuid,
    quantity   int,
    status     text,
    updated_at timestamp,
    PRIMARY KEY ((owner_id), product_id)
);
```

`owner_id` — составное поле: `user_id` для авторизованного, `session_id` для гостя. Поле есть всегда, кардинальность максимальная

`product_id` как clustering key: добавление и удаление товара — это работа
с одной строкой, а не перезапись всей корзины

### Про "горячие" партиции

Partition key должен быть высококардинальным. Взять `category_id` нельзя: категорий десятки, вся "Электроника" легла бы на один узел — будет "авария", только в Cassandra ее ещё и нечем лечить,
балансировщика там нет.

`user_id` и `owner_id` — это миллионы значений, распределение равномерное по построению

### Про решардинг

Cassandra распределяет партиции по кольцу через consistent hashing. 
При добавлении узла новые vnodes забирают часть диапазонов, и переезжает только эта часть — примерно `1/N` данных.

Получается масштабирование не требует полного перераспределения, и его можно делать в пик

## 10.3. Стратегии восстановления целостности

### Hinted Handoff — во время записи

Если реплика недоступна, координатор сохраняет "подсказку" у себя и досылает запись, когда узел вернётся.

Работает автоматически. Но если узла не было дольше окна, подсказки удаляются, и расхождение остаётся.

```
hinted_handoff_enabled: true
max_hint_window_in_ms: 10800000
```

### Read Repair — во время чтения

При чтении координатор сравнивает ответы реплик и найдя расхождение —  чинит отставшую.

```cql
ALTER TABLE orders_by_user WITH read_repair = 'BLOCKING';
```

`BLOCKING` — ответ клиенту отдаётся только после починки. Надёжно, но добавляет задержку.

Чинит только те строки, которые кто-то прочитал. Данные, которые не читают, остаются расходящимися сколько угодно долго.

### Anti-Entropy Repair — планово

Полная сверка реплик через Merkle-деревья:

```bash
nodetool repair -pr keyspace_name
```

Единственный механизм, который чинит всё, включая данные, которые никто не читает. Тяжёлая операция, запускается по расписанию в часы минимальной нагрузки.

### Что для каких данных

**orders — максимальные гарантии**

```cql
CREATE TABLE orders_by_user (...)
  WITH read_repair = 'BLOCKING';
```

Плюс ежедневный `nodetool repair` ночью

**carts — скорость важнее гарантий**

```cql
CREATE TABLE carts_by_owner (...)
  WITH read_repair = 'NONE';
```

Hinted handoff при этом работает и закрывает короткие отказы узлов.

### Сводка

| Данные | Запись | Чтение | Read Repair | nodetool repair |
|---|---|---|---|---|
| `orders_by_user` | QUORUM | QUORUM | BLOCKING | ежедневно |
| `orders_by_id` | QUORUM | QUORUM | BLOCKING | ежедневно |
| `carts_by_owner` | LOCAL_ONE | LOCAL_ONE | NONE | не нужен, TTL |

Логика компромисса одна и та же во всех строках: чем выше уровень согласованности, тем больше узлов должны ответить и тем выше задержка.
