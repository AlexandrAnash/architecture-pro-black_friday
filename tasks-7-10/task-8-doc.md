# Задание 8. Выявление и устранение "горячих" шардов

Проблема: Из-за категории «Электроника» произошла перегрузка одного из шардов MongoDB, так как 70% запросов приходилось именно на эти товары.

Нужно научиться такое замечать и уметь лечить.

## Главная мысль

**Балансировщик MongoDB выравнивает объём данных, а не нагрузку.**

Он считает байты на шардах и перетаскивает чанки, пока их не станет поровну.
Сколько запросов приходит на эти байты — он не знает, такой метрики
у него просто нет.

Отсюда следствие: кластер может быть идеально ровным с точки зрения MongoDB, как у нас 
всего документов: 1000
shard1  документов: 492  (49.2 %)  байт: 23059
shard2  документов: 508  (50.8 %)  байт: 23831

и при этом лежать из-за одного шарда. Поэтому мерить надо:
1) Как лежат данные (у нас нормально)
2) Как идут запросы (вот это менее контролируемо в моменте)

---

## Метрики

### 1.1 Как данные разложены по шардам

```js
const s = db.getSiblingDB("somedb").runCommand({ collStats: "helloDoc" });
print("всего документов: " + s.count);
Object.keys(s.shards).sort().forEach(function (shard) {
  const v = s.shards[shard];
  print(shard + "  документов: " + v.count +
        "  (" + (v.count / s.count * 100).toFixed(1) + " %)  байт: " + v.size);
});
```

Результат:
```
всего документов: 1000
shard1  документов: 492  (49.2 %)  байт: 23059
shard2  документов: 508  (50.8 %)  байт: 23831
```

49.2 % против 50.8 % — норма. Данные разложены поровну, потому что шард-ключ `{ name: "hashed" }` равномерно размазал документы по диапазону хешей.

**Порог тревоги: отклонение больше 20 % от среднего.** При двух шардах среднее
равно 50 %, значит разбираться нужно начиная примерно с 60/40.

### 1.2 Куда идут запросы
Сначала узнаём, какой узел сейчас PRIMARY — клиентские запросы идут только туда:

```js
rs.status().members.find(m => m.stateStr == "PRIMARY").name
```

Затем на этом узле:

```js
db.serverStatus().opcounters
```

Результат:

```
shard1-2 (PRIMARY)   query=5439  insert=505  update=42321  delete=22
shard2-2 (PRIMARY)   query=5098  insert=1    update=0      delete=0
```

**Порог тревоги: разброс операций между шардами `max/avg > 1.5`.**

### 1.3 Насколько быстро шард отвечает

```js
db.serverStatus().opLatencies;
```

**Порог: рост среднего вдвое относительно обычного значения.**

### 1.4 Не уперся ли шард в предел

```js
// очередь операций, ждущих своей очереди
db.serverStatus().globalLock.currentQueue

// свободные слоты параллелизма WiredTiger
db.serverStatus().wiredTiger.concurrentTransactions

// использование кеша в процентах
const c = db.serverStatus().wiredTiger.cache;
print((c["bytes currently in the cache"] / c["maximum bytes configured"] * 100).toFixed(1) + " %");

// память процесса
db.serverStatus().mem
```

`currentQueue` больше нуля означает, что запросы стоят и ждут — шард не успевает.

`concurrentTransactions` — это слоты на одновременное выполнение операций.
Когда свободных не остаётся, новые операции встают в очередь. Самый надёжный
признак того, что шард насыщен.

**Пороги: очередь устойчиво > 0; свободных слотов < 10; кеш > 80 %.**

### 1.5 Отставание реплик

```js
rs.printSecondaryReplicationInfo()
rs.printReplicationInfo()
```

Перегруженный PRIMARY может не успевать отдавать oplog, и реплики начинают отставать. 
Если с них читают — пользователи видят устаревшие данные.

**Порог: отставание больше 10 секунд.**


## Что делать, когда перекос найден
Примеры перекоса:
**Данных** — на одном шарде больше документов и байт. Можно раздробить чанки через splitFind
```
sh.splitFind("somedb.products", { category_id: "electronics" })
sh.moveChunk("somedb.products", { category_id: "electronics" }, "shard2")
```

**Нагрузки** — документов поровну, а `opcounters` разъезжаются. Причина
в том, что популярные данные лежат на одном шарде. Поэтому:
1) можно в Redis положить популярные товары.
2) Увести чтение каталога на реплики 
3) Выделить "горячие" категории в отдельные шарды

**Отдельного документа** — растет `writeConflicts`. Это конкуренция за один документ, например за остаток популярного товара. Лечится изменением схемы, например, по геозонам разбить.


## Профилактика
Дашборд, где метрики всех шардов видны рядом

Алерт на разброс операций `max/avg > 1.5`. 

Шарды добавлять заранее, до пика, а не во время.

Кеш на популярные категории включать сразу — они могут быть известны из аналитики
